# المرحلة صفر — تأسيس مصنع الألعاب التلقائي
## ورشة الشرارات | وثيقة قرارات المنتج والهندسة — 0.1

**الحالة:** مسودة تأسيسية معتمدة مبدئيًا للتوجيه، وليست إعلانًا عن اكتمال التنفيذ.  
**الهدف:** تحويل الورشة من محرر أولي إلى مصنع ألعاب متقدم يعمل بالأنظمة الجاهزة والتركيب المرئي، دون اشتراط نموذج ذكاء اصطناعي توليدي.

---

## 1. القرار الجوهري

ورشة الشرارات لن تعتمد على الذكاء الاصطناعي التوليدي في إنشاء الألعاب أو تعديلها أو تشغيلها. قلب المنتج سيكون **نظامًا حتميًا لتركيب الألعاب**:

1. يختار المستخدم قالب لعبة أو يبدأ مشروعًا فارغًا.
2. يضيف مكوّنات جاهزة من المكتبة.
3. يركّب السلوكيات والقواعد من واجهات مرئية.
4. يختار الخرائط والرسوم والحركات والأصوات.
5. يفحص النظام التوافق والأخطاء المعروفة.
6. يشغّل معاينة اللعبة ثم يصدرها.

كل وظيفة أساسية يجب أن تعمل دون مفتاح API ودون اتصال بخدمة نموذج لغوي. ويمكن إضافة تكامل AI اختياري مستقبلًا، لكنه لن يكون شرطًا لصناعة الألعاب ولا جزءًا لازمًا من بنية التشغيل.

**تمييز مهم:** سلوك الأعداء داخل اللعبة سيظل ممكنًا عبر الذكاء الاصطناعي التقليدي للألعاب، مثل آلة الحالات المحدودة (FSM)، وشجرة السلوك (Behavior Tree)، وأنظمة اتخاذ القرار القائمة على القواعد. هذا ليس ذكاءً اصطناعيًا توليديًا ولا يحتاج إلى نموذج لغوي.

## 2. ما الذي راجعناه في المشروع الحالي؟

المستودع الحالي `codemjd/mini` يحتوي على أساس قابل لإعادة الاستخدام، لذلك لا نوصي بإعادة كتابة كل شيء من الصفر.

### موجود بالفعل في فرع الأساس الذي تمت مراجعته

- محرر مشاهد مستقل يرسم عبر Canvas 2D.
- نموذج مشروع ذي إصدارات وترحيل للبيانات القديمة.
- إدارة متعددة المشاهد، حتى 30 مشهدًا وفق README الحالي.
- إضافة عناصر وتحريكها وتعديل خصائصها وترتيبها وقفلها.
- تراجع وإعادة وحفظ محلي واستيراد وتصدير JSON.
- مكتبة أولية من 12 عنصرًا متجهيًا وتركيبات جاهزة وخلفيات.
- معاينة لعب منفصلة تعمل بمحرك melonJS 20.15.1.
- قواعد أحداث وإجراءات محدودة دون كتابة كود.
- أوامر عربية محلية محددة بقائمة مسموح بها، وليست محادثة حرة أو نموذج AI.
- إعداد بناء Android تجريبي عبر GitHub Actions وCapacitor.

### ما يزال ناقصًا أو محدودًا

- مكتبة أصول احترافية كبيرة مع بيانات ترخيص واضحة.
- نظام مكوّنات وسلوكيات مستقل وقابل لإعادة الاستخدام بين الألعاب.
- محرر مرئي متقدم للمنطق: شروط مركبة، مجموعات، تفرعات، ومخططات عقد.
- أنظمة جاهزة متكاملة للألعاب، لا مجرد إضافة كائنات مفردة.
- محررات متخصصة للحركة والإطارات والصوت والخرائط وواجهات اللعبة.
- مولّد خرائط ومحتوى إجرائي مضبوط بقواعد.
- أداة فحص واختبار تلقائي ذات تقارير واضحة.
- أكاديمية دروس تفاعلية مدمجة.
- تخزين مشاريع وأصول أكثر قوة من الاعتماد على localStorage وحده.
- التحقق من APK على جهاز Android فعلي، ثم بناء إصدار Release موقّع.

**حدود الأدلة:** وثائق طلب الدمج المفتوح تشير إلى نجاح فحوص وبناء APK تجريبي عند commits محددة، لكنها لا تثبت أن أحدث نسخة اختُبرت على جهاز فعلي. كما أن APK التجريبي Debug ليس إصدارًا موقّعًا للنشر. يجب ربط كل نتيجة اختبار برقم commit محدد.

## 3. القرار التقني المبدئي

### الاتجاه المختار: الويب أولًا، ومحرك تشغيل منفصل

نحتفظ مبدئيًا بالأساس التالي:

- **واجهة الورشة:** تطبيق ويب عربي يعمل باللمس، مع تصميم Mobile-first.
- **محرر المشاهد:** Spark Canvas Editor مستقل عن محرك تشغيل اللعبة.
- **محرك تشغيل الألعاب:** melonJS، عبر طبقة Spark Runtime ومحوّل يحول وثيقة المشروع إلى مشهد قابل للتشغيل.
- **وصف المشروع:** وثيقة بيانات ذات إصدار واضح، لا تعتمد على DOM ولا على حالة الواجهة.
- **تركيب السلوكيات:** مكوّنات وموارد وقواعد مرئية ذات مخططات بيانات موثقة.
- **بناء Android:** خط بناء سحابي عبر GitHub Actions/Capacitor؛ لا يُشترط تثبيت Android Studio على هاتف المستخدم.

لا نبدأ الآن باقتصاص Godot أو إنشاء نسخة مشتقة منه. السبب ليس ضعف Godot؛ بل إن المشروع لديه محرر ويب قائم، وهذا الاتجاه أقرب إلى استخدامه من الهاتف، وأقل مخاطرة من استبدال الأساس كاملًا في هذه المرحلة.

محرك melonJS يقدم حاليًا مسارات عرض WebGPU وWebGL 2 وCanvas 2D، مع أنظمة للخرائط والتصادم والصوت والإدخال والرسوم المتحركة. سنستخدم ما يخدم نطاق ألعاب 2D أولًا، ونؤجل ميزات 3D/2.5D إلى قرار مستقل بعد إثبات جودة النسخة الأساسية.

### حدود هذا القرار

هذا اختيار معماري مبدئي قابل للمراجعة بعد اختبار الأداء والميزات المطلوبة. لا يعني أن melonJS وحده سيقدم كل أدوات صناعة الألعاب؛ طبقة Spark ستبني المحررات ومكتبة الأنظمة وسير العمل فوقه.

## 4. بنية مصنع الألعاب المقترحة

### أ. وثيقة المشروع

تتكون وثيقة المشروع من:

- إعدادات اللعبة: الاسم، الأبعاد، الاتجاه، معدل الإطارات، إعدادات اللمس.
- المشاهد والمراحل والانتقالات بينها.
- الكائنات ومكوّناتها.
- قواعد الأحداث والشروط والإجراءات.
- المراجع إلى الأصول والحزم.
- القوالب والتركيبات القابلة لإعادة الاستخدام.
- إعدادات التصدير والاختبار.
- بيانات تقدم الدروس المرتبطة بالمشروع، منفصلة عن محتوى اللعبة.

كل نوع بيانات له إصدار ومخطط تحقق وترحيل. يجب أن يمكن فتح مشروع قديم دون فقد بياناته عند تطوير الورشة.

### ب. نظام المكوّنات

المكوّن يضيف قدرة واضحة إلى الكائن، ويُضبط عبر خصائص آمنة بدل كتابة كود. أمثلة:

- Transform: الموقع والحجم والدوران.
- Visual/Sprite: الصورة والإطار والشفافية والطبقة.
- Animation: الحركة ومجموعة الإطارات وسرعة التشغيل.
- Collider: شكل التصادم ونوعه.
- Movement: الحركة والسرعة والتسارع.
- Health: الصحة والضرر والمناعة.
- Combat: الهجوم والمدى والتبريد.
- Collectible: الالتقاط والقيمة.
- Inventory: العناصر والحدود.
- CameraTarget: متابعة الكاميرا.
- AudioEmitter: المؤثرات والأصوات.
- UIWidget: عناصر الواجهة والتفاعل.

لا نفعّل جميع المكوّنات على كل كائن؛ نضيف فقط ما يحتاجه، مع منع التراكيب المتعارضة.

### ج. مكتبة السلوكيات

تكون السلوكيات وحدات قابلة لإعادة الاستخدام، مثل:

- لاعب يتحرك بعصا لمس أو لوحة مفاتيح.
- عدو يحرس منطقة أو يطارد أو يهرب أو يهاجم عن بُعد.
- دورية ذهاب وإياب.
- قفز ومنصات.
- جمع عناصر وفتح أبواب.
- حياة وضرر وشفاء.
- موجات أعداء وزعيم.
- حوار وتفاعل مع عناصر البيئة.

تُبنى السلوكيات المتقدمة من حالات وشروط وإجراءات معروفة، وتُختبر كوحدات مستقلة.

### د. محرر المنطق المرئي

يكون سهلًا على الهاتف:

**عند حدوث حدث → افحص شروطًا → نفّذ إجراءات.**

مثال: عند جمع المفتاح، وإذا كان عدد المفاتيح 3، افتح البوابة واعرض رسالة.

يبدأ المحرر ببطاقات واضحة للمبتدئ، ثم يفتح وضعًا متقدمًا للمجموعات والتفرعات والعقد. لا نجعل Spark Script شرطًا لصناعة لعبة؛ يبقى أداة اختيارية للمستخدم المتقدم فقط.

### هـ. القوالب والتركيبات

القالب لعبة مصغرة كاملة قابلة للتعديل، وليس مجرد خلفية أو مجموعة صور. أمثلة للأنواع المستهدفة:

- منصات.
- قتال ساحات.
- مغامرة من أعلى.
- نجاة.
- دفاع أبراج.
- ألغاز.
- سباق.
- إطلاق نار ثنائي الأبعاد.

والتركيبة جزء قابل للإضافة إلى أي مشروع، مثل بوابة ومفتاح، موجة أعداء، نظام حياة، صندوق غنائم، أو قائمة توقف.

### و. المحتوى الإجرائي

توليد المحتوى هنا مبني على قواعد قابلة للتحكم، مثل إنشاء توزيع خرائط أو غرف أو أعداء أو مكافآت من بذرة عشوائية قابلة لإعادة الإنتاج. يجب أن يستطيع المستخدم مراجعة النتيجة وتعديلها، لا أن تكون عملية غامضة.

### ز. الفحص والاختبار

تتضمن الورشة فحوصًا قبل المعاينة والتصدير، منها:

- التحقق من المراجع المفقودة والأصول غير المتاحة.
- كشف الكائنات الخارجة عن حدود المشهد.
- كشف مكوّنات متضاربة أو قواعد مستحيلة.
- التحقق من وجود نقطة بدء ونقطة نهاية عندما يتطلب القالب ذلك.
- اختبار إجراءات اللعبة الأساسية بسيناريوهات مسجلة.
- تقرير واضح: خطأ يمنع البناء، تحذير، أو اقتراح تحسين.

لا ندّعي إصلاح أي شيء تلقائيًا إلا عندما توجد قاعدة إصلاح معروفة ويمكن التحقق من نتيجتها.

## 5. الأكاديمية التفاعلية — جزء أساسي من المنتج

لن تكون الدروس صفحة مقالات أو روابط فيديو فقط. ستكون **مدرسة عملية داخل المحرر**؛ يتعلم المستخدم بتنفيذ المهمة داخل مشروع تدريبي، مع تحقق آلي من إنجاز كل خطوة.

### مواصفات كل درس

1. هدف تعلم واحد واضح.
2. شرح مصور أو حركة قصيرة داخل الواجهة.
3. تمييز الأداة التي يجب استخدامها.
4. خطوة عملية ينفذها المتعلم في المحرر.
5. تحقق تلقائي من النتيجة.
6. تلميح أول ثم تلميح أوضح عند التعثر.
7. شرح للخطأ الشائع وكيفية إصلاحه.
8. تحدٍّ صغير دون إرشادات كاملة.
9. حفظ التقدم وإمكانية إكمال الدرس لاحقًا.
10. زر إعادة المحاولة واستعادة المشروع التدريبي.

الدروس تُخزّن بصيغة بيانات قابلة للتوسعة، بحيث يمكن إضافة درس جديد دون إعادة برمجة نظام الأكاديمية. وتعمل الدروس الأساسية محليًا دون خدمة AI.

### خريطة الأكاديمية المستهدفة

الهدف طويل الأمد هو مكتبة تضم **100 درس تفاعلي أو أكثر**. يبدأ الإطلاق بمجموعة تأسيسية لا تقل عن 30 درسًا مكتملًا، ثم تُضاف المجموعات التالية بالتدريج:

| المسار | أمثلة المحتوى | الهدف المبدئي |
|---|---|---:|
| البداية واستخدام الورشة | إنشاء مشروع، التنقل، الحفظ، النسخ والتراجع | 10 |
| المشاهد والرسم والأصول | المشاهد، الطبقات، الخلفيات، العناصر، الاستيراد | 15 |
| الحركة والتصادم | اللاعب، اللمس، الحركة، القفز، التصادم | 15 |
| المنطق والسلوك | الأحداث، الشروط، الإجراءات، الأعداء | 20 |
| أنظمة الألعاب | القتال، الصحة، الأغراض، المراحل، القوائم | 20 |
| الإتقان والإصدار | التحريك، الصوت، الاختبار، الأداء، التصدير | 20 |
| **المجموع المستهدف** |  | **100** |

يُضاف إلى ذلك تحديات حرة ومشاريع تخرج، ولا تُحسب هذه التحديات ضمن عدد الدروس الأساسي.

### أساليب التعلم داخل الورشة

- جولة إرشادية عند فتح أداة جديدة.
- درس خطوة بخطوة مع إبراز مكان النقر.
- تحدٍّ مصغر يطلب من المتعلم إنجاز هدف.
- مشروع تدريبي يزداد تعقيدًا تدريجيًا.
- مراجعة قصيرة بعد كل وحدة.
- مسارات للمبتدئ والمتوسط والمتقدم.
- فهرس للمهارات مع إظهار ما أتقنه المستخدم وما لم يتقنه.

يجب ألا يُجبر المستخدم على إنهاء الدروس قبل استخدام المحرر؛ يمكنه التعلم أو الإنشاء بحرية.

## 6. الأصول والحقوق

- تبقى شيفرة Spark التي نؤلفها تحت سيطرة مالك المشروع، ولا ننسخ مكونات محرك آخر بطريقة تجعل المشروع تابعًا لترخيص غير مناسب.
- كل مكتبة خارجية تحتفظ بترخيصها وإشعاراتها المطلوبة.
- كل أصل مرئي أو صوتي يسجل له: المصدر، المنشئ، الترخيص، السماح بالاستخدام التجاري، السماح بالتعديل، وشروط إعادة التوزيع.
- لا تُدخل حزمة أصول إلى المكتبة لمجرد أنها مجانية؛ يجب فحص ترخيصها.
- لا تُضاف أصول ذات ترخيص غير واضح إلى القوالب الرسمية.
- قبل التوزيع التجاري، يُنجز جرد تراخيص لكل الاعتماديات والأصول.

**ملاحظة حول المستودع:** المستودع الحالي عام على GitHub. الظهور العام لا ينقل حقوق التأليف تلقائيًا، لكنه يجعل الشيفرة مرئية. لا نضيف ترخيصًا مفتوحًا جديدًا إلى شيفرة Spark دون قرار صريح من مالك المشروع. وإذا كان المطلوب إخفاء الشيفرة، فذلك يستلزم أيضًا مراجعة إعدادات خصوصية المستودع.

## 7. استراتيجية الهاتف والتصدير

- تأليف الألعاب من متصفح الهاتف هو المسار الأساسي.
- تصميم الواجهة للمس والشاشة الصغيرة، مع دعم الوضع الأفقي عند الحاجة.
- ندرس إضافة PWA وتخزين محلي قوي؛ لا نفترض أن التطبيق الحالي يعمل دون اتصال كاملًا قبل تنفيذ واختبار التخزين المؤقت.
- ننتقل من localStorage إلى IndexedDB أو تخزين ملفات مشروع مناسب للمشاريع والأصول الكبيرة.
- التصدير الأولي: مشروع ويب مستقل قابل للتنزيل.
- تصدير Android: بناء سحابي في GitHub Actions، مع فصل APK Debug للاختبار عن APK Release الموقّع للتوزيع.
- لا يُعلن نجاح إصدار Android قبل تثبيته وتشغيله فعليًا على جهاز Android، واختبار اللمس والحفظ والاستئناف والخروج.

بناء Android محليًا عبر Capacitor يتطلب بيئة Node وAndroid Studio وAndroid SDK؛ لذلك لا نعتمد على أن المستخدم سيبني APK داخل هاتفه. نستثمر في خط البناء السحابي القائم، ثم نطوره إلى إصدار Release موثوق.

## 8. ما لن ننفذه في المرحلة صفر

- لن ندرّب نموذج ذكاء اصطناعي.
- لن نجعل مفتاح API شرطًا.
- لن نبدأ باقتصاص Godot أو صنع محرك جديد من الصفر.
- لن نضيف محررات كثيرة قبل تثبيت نموذج المشروع والمكوّنات.
- لن نعد بأن كل أنواع الألعاب أو 3D ستكون مدعومة في أول إصدار.
- لن ندمج طلب الدمج المفتوح رقم 2 أو نغيّر فرع main ضمن هذه الوثيقة.
