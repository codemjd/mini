# المرحلة صفر — عقد المكونات ومنطق اللعب
## سجل المكونات والأحداث والشروط والإجراءات — 0.2

**الغرض:** تحديد أول واجهة موحدة لمصنع الألعاب. هذه مواصفات تصميمية للمرحلة التالية، وليست ادعاءً بأن كل العناصر منفذة في المحرك الحالي.

## 1. التوافق مع الأساس الحالي

المشروع الحالي يحتوي على:
- كائنات: hero, enemy, coin, crate, platform.
- سلوكيات تشغيل: player-control, follow-target, collectible, health, melee.
- أحداث: game-start, coin-collected, enemy-defeated, player-hit, score-reached.
- إجراءات: show-message, heal-player, set-player-speed, set-player-damage, finish-level.
- نموذج مشروع v5 متعدد المشاهد، ونظام قواعد محدود.

يجب أن تعمل التوسعة عبر طبقة ترحيل توافقية. لا نحذف الحقول الحالية ولا نغيّر معنى القواعد القديمة أثناء إضافة المكونات الجديدة. تُحوّل المشاريع القديمة تدريجيًا إلى تمثيل المكونات، مع الاحتفاظ بقراءة v1-v5.

## 2. أول 12 مكوّنًا

المكوّنات التالية هي أول سجل موحد. يمكن أن يحتوي الكائن على أكثر من مكوّن، لكن بعض التركيبات تتطلب شروط توافق.

| المكوّن | الوظيفة | الأولوية |
|---|---|---|
| Transform | الموقع والحجم والدوران والطبقة | أساسي |
| Visual | اللون والصورة والشفافية والظهور | أساسي |
| Animation | الحركة والإطارات والسرعة | أساسي |
| Collider | حدود التصادم ونوعه | أساسي |
| Movement | سرعة الحركة والتسارع والاتجاه | أساسي |
| PlayerInput | ربط الإدخال باللاعب | أساسي |
| Health | الصحة القصوى والحالية والمناعة | أساسي |
| Combat | الهجوم والضرر والمدى والتبريد | أساسي |
| Collectible | قابلية الجمع والقيمة | أساسي |
| EnemyBrain | الحراسة والمطاردة والهروب والدورية | أساسي |
| TriggerZone | منطقة تفعيل عند الدخول/الخروج | لاحق |
| AudioEmitter | مؤثر صوتي عند حدث معين | لاحق |

### قواعد التوافق

- Transform واحد فقط لكل كائن.
- Visual واحد على الأقل لكل كائن مرئي.
- PlayerInput لا يضاف إلا لكائن لاعب محدد، ولا يسمح بأكثر من لاعب أساسي واحد في قالب اللاعب الواحد.
- Health مطلوب للأعداء الذين يمكن هزيمتهم.
- Combat يحتاج هدفًا صالحًا ومكوّن Health على الهدف.
- Collectible لا يجتمع مع EnemyBrain على الكائن نفسه في النسخة الأولى.
- Collider مطلوب للتصادم والجمع والمناطق.
- EnemyBrain يحتاج Movement وCollider، ويمكنه استخدام Health وCombat.
- Animation اختيارية، وتعود Visual إلى رسم ثابت عند غيابها.
- TriggerZone لا يتطلب أن يكون مرئيًا.

### خصائص قابلة للتحرير

كل خاصية لها نوع وقيود وقيمة افتراضية ووحدة قياس عند الحاجة. لا نعرض للمستخدم حقولًا تقنية غير مفهومة؛ مثلًا تعرض السرعة بوصفها «سرعة الحركة»، والتبريد بوصفه «الوقت قبل الهجوم التالي».

## 3. أول 10 أحداث

الأحداث هي ما يبدأ تنفيذ القاعدة. القائمة التالية توسعة مستقبلية فوق الأحداث الخمسة الحالية.

| الرمز | الاسم الظاهر | الحالة في الأساس الحالي |
|---|---|---|
| game-start | عند بدء اللعبة | موجود |
| scene-start | عند بدء المشهد | جديد |
| coin-collected | عند جمع عنصر | موجود |
| enemy-defeated | عند هزيمة عدو | موجود |
| player-hit | عند إصابة اللاعب | موجود |
| score-reached | عند بلوغ نقاط محددة | موجود |
| health-below | عندما تنخفض الصحة إلى حد | جديد |
| object-entered-zone | عند دخول منطقة | جديد |
| timer-finished | عند انتهاء مؤقت | جديد |
| button-pressed | عند الضغط على زر واجهة | جديد |

كل حدث يحدد بياناته المسموح بها. مثال: health-below يتطلب هدفًا وحدًا أدنى، وobject-entered-zone يتطلب منطقة وكائنًا.

## 4. أول 20 شرطًا

الشرط يقرر هل تنفذ القاعدة أم لا. تدعم الواجهة دمج الشروط باستخدام «كل الشروط» أو «أي شرط» في المستوى الأول، ثم مجموعات متداخلة في محرر متقدم.

| # | الشرط | مثال |
|---:|---|---|
| 1 | score-at-least | النقاط 10 أو أكثر |
| 2 | score-equals | النقاط تساوي 5 |
| 3 | health-at-most | صحة اللاعب 20 أو أقل |
| 4 | health-at-least | صحة اللاعب 50 أو أكثر |
| 5 | object-exists | كائن معين موجود |
| 6 | object-is-alive | الكائن ما زال حيًا |
| 7 | object-is-visible | الكائن ظاهر |
| 8 | object-is-enabled | الكائن مفعّل |
| 9 | distance-at-most | المسافة أقل من 100 |
| 10 | distance-at-least | المسافة أكبر من 200 |
| 11 | counter-at-least | العداد 3 أو أكثر |
| 12 | counter-equals | العداد يساوي 0 |
| 13 | timer-at-least | مرّ 30 ثانية |
| 14 | timer-at-most | بقي أقل من 5 ثوانٍ |
| 15 | item-owned | اللاعب يملك عنصرًا |
| 16 | scene-is | المشهد الحالي هو المحدد |
| 17 | input-held | زر معين مضغوط |
| 18 | random-chance | احتمال محدد بالمئة |
| 19 | variable-equals | متغير يساوي قيمة |
| 20 | variable-at-least | متغير يبلغ قيمة أو يتجاوزها |

تُقيّد القيم الرقمية بحدود مناسبة. لا يُسمح بشرط يقرأ متغيرًا غير موجود، أو يقارن نوعين غير متوافقين.

### قواعد التنفيذ الآمن

- لا يوجد تنفيذ نص برمجي حر أو eval.
- لا يستطيع الإجراء الوصول إلى ملفات أو شبكة أو واجهات الجهاز.
- كل إجراء يملك مخطط مدخلات ثابتًا، وفحص توافق قبل الحفظ.
- تُرفض الأهداف غير الموجودة قبل المعاينة أو التصدير.
- الإجراءات التي قد تحذف كائنات أو تغيّر المشهد يجب أن تكون قابلة للتراجع في المحرر، وتعمل في Runtime وفق دورة تحديث آمنة.
- تُسجّل أحداث التنفيذ في تقرير تصحيح يمكن للمستخدم فهمه.

## 6. ترتيب التنفيذ المرحلي

### الدفعة A — أول قالب قابل للعب
- Transform, Visual, Collider, Movement, PlayerInput, Health, Combat, Collectible, EnemyBrain.
- الأحداث الخمسة الحالية مع scene-start.
- الشروط: health-at-most, object-exists, object-is-alive, distance-at-most, counter-at-least.
- الإجراءات: الرسالة، الشفاء، الضرر، ضبط السرعة والضرر، النقاط، العداد، الإظهار والإخفاء، إنشاء كائن، إنهاء المرحلة.

### الدفعة B — لعبة أعمق
- Animation, TriggerZone, AudioEmitter.
- المؤقتات والمناطق والأزرار.
- المتغيرات وتغيير المشاهد والتفعيل والتعطيل.

### الدفعة C — أدوات متقدمة
- مجموعات شروط متداخلة.
- إجراءات مركبة.
- محرر مخطط عقد اختياري.
- حزم سلوكيات قابلة للتبادل.

لا يبدأ تطوير جميع 30 إجراءً قبل اختبار الدفعة A على مشروع لعبة حقيقي.

## 7. معايير القبول

- يستطيع المبتدئ تركيب لاعب يتحرك ويجمع عنصرًا دون كود.
- يستطيع إعداد عدو يطارد اللاعب ويتلقى الضرر.
- يستطيع إنشاء قاعدة «عند جمع 3 بلورات، اعرض رسالة وافتح البوابة».
- تظهر الأخطاء قبل التشغيل مع شرح سببها وطريقة إصلاحها.
- لا تؤدي القاعدة غير الصالحة إلى توقف المحرك.
- تظل قواعد المشاريع القديمة قابلة للتحميل والتشغيل.
- يمكن حفظ المشروع وإغلاقه وفتحه دون فقد المكونات أو القواعد.
