# المرحلة الأولى — قائمة التنفيذ المرتبة
## تحويل وثائق المرحلة صفر إلى خطة عمل — 0.1

**الحالة:** قائمة مهام تنفيذية أولية. لا تعني أن هذه المهام نُفذت.  
**قاعدة التنفيذ:** كل دفعة تنتهي باختبارات قبول، ولا ننتقل إلى الدفعة التالية إذا فقدت المشاريع القديمة توافقها.

## الهدف من المرحلة الأولى

بناء أساس صغير لكنه حقيقي لمصنع الألعاب: مشروع موحد، سجل مكونات، سلوكيات قابلة للتركيب، قواعد لعب آمنة، وأول درس تفاعلي يعمل داخل المحرر على الهاتف.

**ليس هدف المرحلة الأولى** إنشاء 100 درس أو 30 نوع لعبة أو مكتبة أصول ضخمة. نثبت النظام عبر لعبة صغيرة متكاملة أولًا.

## الدفعة 1 — حماية الأساس وتثبيت نموذج المشروع

### المهام
- [ ] إضافة اختبارات قراءة وكتابة لمشاريع v1-v5.
- [ ] إنشاء مخطط مشروع جديد ذي إصدار واضح مع ترحيل v5 دون فقد بيانات.
- [ ] فصل بيانات الكائنات عن بيانات العرض.
- [ ] إضافة معرفات مستقرة للمكونات والسلوكيات.
- [ ] منع التكرار والمراجع المكسورة والقيم الخارجة عن الحدود.
- [ ] حفظ نسخة احتياطية قبل أي ترحيل تلقائي.
- [ ] توحيد الحفظ والتحميل والتصدير والاستيراد عبر خدمة مشروع واحدة.

### قبول الدفعة
- مشروع v5 قديم يفتح كما كان.
- المشروع بعد الحفظ وإعادة الفتح يحتفظ بالمشاهد والكائنات والقواعد.
- ملف تالف لا يمسح آخر حفظ سليم.
- لا تتغير نتائج لعبة قديمة دون سبب موثق.

## الدفعة 2 — سجل المكونات

### المهام
- [ ] إنشاء Component Registry موحد.
- [ ] تعريف المخطط والخصائص الافتراضية لكل مكوّن.
- [ ] إضافة تحقق التوافق والتعارض.
- [ ] إنشاء واجهة إضافة/حذف مكوّن.
- [ ] إنشاء محرر خصائص عربي يعتمد على نوع الخاصية.
- [ ] إنشاء محول توافق يربط الحقول القديمة بمكونات Transform/Visual/Movement/Health.
- [ ] إضافة سجل أخطاء يوضح سبب رفض مكوّن أو قيمة.

### نطاق الدفعة الأولى
Transform, Visual, Collider, Movement, PlayerInput, Health, Combat, Collectible, EnemyBrain.

### قبول الدفعة
- يمكن إنشاء لاعب من مكونات دون الاعتماد على كائن hero ذي خصائص ثابتة فقط.
- يمكن إنشاء عدو حارس أو مطارد من نفس المكونات مع اختلاف الإعدادات.
- تغيير خاصية لا يفسد المشهد ولا يغير كائنًا آخر.
- المشروع القديم يظل قابلًا للتحرير والمعاينة.

## الدفعة 3 — محرك السلوكيات والقواعد

### المهام
- [ ] بناء سجل أحداث وشروط وإجراءات.
- [ ] إضافة شروط مركبة من نوع «كلها» و«أي منها».
- [ ] فصل تعريف القاعدة عن تنفيذها في Runtime.
- [ ] إضافة فحص مسبق للقواعد قبل المعاينة.
- [ ] إضافة سجل تشغيل يمكن قراءته للمبتدئ.
- [ ] دعم تراجع/إعادة تغييرات القواعد.
- [ ] إضافة اختبارات لكل حدث وشرط وإجراء.

### الحد الأدنى المطلوب
- 6 أحداث: game-start, scene-start, coin-collected, enemy-defeated, player-hit, score-reached.
- 5 شروط أولية: health-at-most, object-exists, object-is-alive, distance-at-most, counter-at-least.
- 10 إجراءات أولية: show-message, heal-player, damage-object, set-player-speed, set-player-damage, add-score, add-counter, show-object, hide-object, finish-level.

لا نفعّل القائمة الكاملة ذات 20 شرطًا و30 إجراءً دفعة واحدة. تضاف بعد إثبات الاستقرار واحتياج القوالب إليها.

### قبول الدفعة
- قاعدة «عند جمع 3 بلورات، اعرض رسالة» تعمل في المعاينة.
- القاعدة غير الصالحة تُرفض قبل التشغيل برسالة مفهومة.
- لا تتكرر القاعدة ذات التنفيذ لمرة واحدة بصورة غير مقصودة.
- لا يوجد تنفيذ JavaScript حر أو eval.

## الدفعة 4 — تركيب قالب لعبة حقيقي

### القالب الأول: لعبة جمع البلورات

يتكون من:
- لاعب يتحرك باللمس.
- بلورات قابلة للجمع.
- عدو بدورية أو مطاردة.
- صحة وضرر.
- عداد نقاط.
- بوابة أو هدف نهاية.
- شاشة نجاح وإعادة المحاولة.

### المهام
- [ ] بناء قالب كامل باستخدام المكونات الجديدة.
- [ ] حفظ القالب كمصدر قابل للنسخ، لا كحالة خاصة في الكود.
- [ ] إضافة تركيبتين Prefabs على الأقل: لاعب جاهز، وعدو حارس.
- [ ] إضافة فحص صلاحية القالب.
- [ ] اختبار اللعب على الهاتف.

### قبول الدفعة
يمكن إنشاء اللعبة من القالب، تعديل عناصرها، حفظها، إعادة فتحها، وتشغيلها دون كود.

## الدفعة 5 — محرك الدروس التفاعلية

### المهام
- [ ] إنشاء مخطط بيانات للدرس والخطوة والتلميح ومعيار الإنجاز.
- [ ] إنشاء مشروع تدريب منفصل عن مشاريع المستخدم.
- [ ] إنشاء محرك تحقق من حالة المشروع.
- [ ] حفظ تقدم الدرس محليًا.
- [ ] دعم إعادة الخطوة وإعادة الدرس وتخطيه.
- [ ] إضافة إبراز الأدوات وإظهار التلميحات تدريجيًا.
- [ ] تسجيل نتائج الاختبارات التعليمية.

### أول درس
«اصنع أول لعبة جمع» وفق وثيقة المرحلة صفر. يبدأ بإضافة لاعب وبلورات، ثم الحركة والجمع والاختبار. لا يُنشر على أنه مكتمل قبل تحقق جميع خطواته آليًا.

### قبول الدفعة
- يستطيع مستخدم مبتدئ إكمال الدرس باللمس دون كتابة كود.
- لا يستطيع اجتياز خطوة قبل تحقيق شرطها.
- إغلاق التطبيق وإعادة فتحه لا يفقد التقدم.
- إعادة الدرس لا تعدل مشروع المستخدم الحقيقي.

## الدفعة 6 — أساس واجهة الهاتف والتخزين

### المهام
- [ ] تطبيق خريطة الأقسام الخمسة.
- [ ] إعادة ترتيب المحرر للوضعين العمودي والأفقي.
- [ ] إضافة بدائل للسحب الدقيق.
- [ ] الانتقال من localStorage إلى IndexedDB للمشاريع والتقدم والأصول عند الحاجة.
- [ ] إضافة حفظ آمن ونسخ احتياطي واستعادة.
- [ ] إضافة حزم Offline للتطبيق والدروس المثبتة.
- [ ] اختبار التبديل بين التطبيقات واستعادة حالة التحرير.

### قبول الدفعة
- إنشاء المشروع وتحريره وحفظه واستعادة الدرس باللمس.
- لا يعتمد حفظ المشروع على بقاء الصفحة مفتوحة.
- تظهر أخطاء التخزين دون فقد آخر نسخة صالحة.

## الدفعة 7 — بوابة الجودة والتصدير

### المهام
- [ ] فحص TypeScript والبناء والاختبارات الآلية.
- [ ] اختبارات المتصفح للهاتف.
- [ ] اختبار أداء المشهد مع أعداد كائنات متدرجة.
- [ ] اختبار حفظ واستعادة مشروع حقيقي.
- [ ] بناء نسخة ويب قابلة للتنزيل.
- [ ] تحديث خط بناء APK Debug.
- [ ] إضافة خط APK Release موقّع بعد توفير أسرار التوقيع بأمان.
- [ ] تثبيت APK على جهاز Android واختبار اللعب والحفظ والعودة من الخلفية.

### قبول الدفعة
لا نعلن إصدارًا مستقرًا قبل نجاح الاختبارات وتوثيق رقم commit والجهاز والنتائج. لا تُحفظ مفاتيح التوقيع أو كلمات المرور داخل المستودع.

## ما لا يدخل المرحلة الأولى

- مكتبة 1000 أصل.
- 100 درس مكتمل.
- جميع أنواع الألعاب.
- محرر 3D.
- محرر عقد متقدم قبل ثبات القواعد الأساسية.
- AI توليدي إلزامي.
- اللعب الشبكي.
- متجر أصول أو نظام حسابات.

هذه عناصر توسعة مستقبلية. الأولوية أن نصنع لعبة واحدة جيدة من داخل الورشة، دون كتابة كود، ونستطيع حفظها وتشغيلها على الهاتف.
